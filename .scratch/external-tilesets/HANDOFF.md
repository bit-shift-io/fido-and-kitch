# Handoff — External Tileset Support for STI

## Summary

The vendored map loader (`lib/sti/`, Simple Tiled Implementation) refuses any map that references an external `.tsx` tileset instead of embedding it — a hard assertion in `lib/sti/init.lua`. This forced the project to keep Tiled's non-obvious "Embed tilesets" Preferences setting enabled, which is easy to forget and produces a divergent exported `.lua` file. Researched alternatives (Cartographer, Advanced Tiled Loader) and found none actively-maintained that solve this out of the box — Cartographer has the identical gap and is more dormant than STI itself. The fix is a small, local patch: a new pure-logic resolver module (`src/map/external_tileset.lua`) that parses a referenced `.tsx` via a newly-vendored XML library (`xml2lua`) and produces a tileset table shaped exactly like STI's own embedded-tileset output, wired in by replacing STI's assertion with a call into it.

Two real tileset shapes exist in this repo and both must work: `res/tilesets/generic_platformer_tiles.tsx` (single shared image on a grid) and `res/tilesets/props.tsx` (an image-collection tileset, one `<image>` per tile, several cropped to a sub-region of a larger source image — this backs the deferred Background prop feature). Per-tile properties and animation are genuinely used by STI today (confirmed by reading `lib/sti/init.lua`); per-tile collision-editor shapes (`objectGroup`) are resolved for parity only — this project's own collision model comes entirely from map-level object layers, not tileset tile colliders.

Full spec: [PRD.md](PRD.md). Rationale, including the STI-vs-Cartographer research and why raw `.tmx` loading was descoped: [DECISIONS.md](DECISIONS.md). Glossary entry added to `CONTEXT.md`: External tileset. No ADRs — the library-vs-patch choice and caching/error-handling decisions are logged in DECISIONS.md; none of them meet the ADR gate (they're reversible and their rationale is fully captured there already).

## Implementation order

1. **01-single-image-external-tileset** — foundation: vendor `xml2lua`, create the resolver module, patch STI, revert `sandbox.tmx`/`sandbox.lua` to an external tileset reference. Everything else builds on this.
2. **02-image-collection-external-tileset** — independent tileset shape; can follow immediately once 01's module/wiring exists.
3. **03-per-tile-properties-animation-collision** — per-tile metadata, applies to both shapes from 01/02.
4. **04-caching** — wraps the resolution entry point once it's stable across all shapes; lowest risk last.

## Implementer notes / gotchas

- **STI's embedded-tileset table shape is the contract.** Before writing `external_tileset`, read how `lib/sti/init.lua` currently builds a tileset table from embedded data (`image`, `imagewidth`/`imageheight`, `tilewidth`/`tileheight`, `columns`, `spacing`, `margin`, `tilecount`, and per-tile `properties`/`animation`/`objectGroup` — see lines documented in DECISIONS.md Q5). The resolver's job is to produce a table indistinguishable from that, not to invent a new shape STI has to special-case.
- **Real fixtures already exist on disk.** `res/tilesets/generic_platformer_tiles.tsx` (grid shape) and `res/tilesets/props.tsx` (image-collection shape, with real cropped tiles like id `3`) are the actual files this feature must handle — use their real content (or exact copies) as test fixtures rather than inventing synthetic XML that might miss a real quirk. This already happened once during planning: the cropped-sub-image requirement wasn't obvious until `props.tsx` was actually read.
- **`xml2lua`'s tree handler**: `local xml2lua = require('lib.xml2lua.xml2lua'); local handler = require('lib.xml2lua.xmlhandler.tree'); local parser = xml2lua.parser(handler); parser:parse(xmlString)` — resulting tree puts attributes under `_attr` on each element table. Confirm the exact vendored path/require pattern matches this project's `lib/` convention (see how `lib/bump`, `lib/hump` are required elsewhere) before assuming the above is exact.
- **Caching seam**: for issue 04's tests to assert "only parsed once" without reaching into internals, give `external_tileset` an injectable file-reader (or parser) dependency — mirrors how other pure modules in this codebase (e.g. `PlayerMovement`, `enemy_brain`) avoid hidden globals. Don't wire the cache in a way that makes it untestable without a real filesystem.
- **Error handling**: loud failure (see DECISIONS.md Q7) — use `error()`/`assert()` with a message that names the offending `.tsx` path, not a generic Lua parse error. A future developer hitting this should immediately know which file is broken.
- **Testability seam pattern**: mirror `src/player/player_movement.lua` / `src/enemy/enemy_brain.lua` — pure decision/transform functions with no LÖVE/globals dependencies where possible, tested in `tests/unit/`, run via `./test-unit.sh`. `external_tileset` can't be fully LÖVE-free (it reads a file from disk), but keep the XML-table-to-tileset-table shaping logic separable from the file I/O so most of it is testable with literal string fixtures.
- **Test runner**: this repo's actual test commands are `./test-unit.sh`, `./test-integration.sh`, `./test-e2e.sh`, `./test-all.sh` — some older `.scratch/` docs in this repo reference a `./test.sh` that does not exist; don't follow that stale reference.
- **Don't touch `sandbox.tmx`'s object layer** — the robot/spider objects added by the previous (enemies) feature live in the real `"game"` objectgroup, not the tileset-tiles section; when reverting the tileset reference to external, only the `tilesets` block should change.
